# Audit Trail — how it works, and what to do before delivery

Operator actions on the HMI are recorded permanently: who did it, what changed,
and when. This note covers what is already configured, what must be changed at
delivery, and what can only be checked on the real panel.

Verified 2026-08-23 by reading the audit database directly, not by assumption.

---

## 1. What is recorded

Every operator command on all 89 valves:

| Action | Tag written |
|---|---|
| OPEN | `V###_OpenCmd` |
| CLOSE | `V###_CloseCmd` |
| ENABLE / DISABLE | `V###_Configured` |
| FAULT RESET | `_TimeoutOpenAlarm`, `_TimeoutCloseAlarm`, `_UnexpMove`, `_DirFault` |

Each record carries the user name, the operator station, the old and new value
and a timestamp. Example, straight out of the database:

```
14:47:44  V021_Configured  User  FALSE -> TRUE   Scripting
14:47:53  V021_OpenCmd     User  FALSE -> TRUE   Scripting
14:48:04  V021_CloseCmd    User  FALSE -> TRUE   Scripting
14:48:15  V021_Configured  User  TRUE  -> FALSE  Scripting
```

Two rows appear per action. `Scripting` with the operator's name is the
intent; `Event Manager` with user `System` is the system's reaction. That
pairing is Siemens' design, not duplication — filter on `Scripting` to see
operator actions alone.

Valve feedback signals (`OpenFB`, `ClosedFB`, `Healthy`, `LocalMode`, `State`)
are deliberately **not** audited. They are driven by the PLC, and Siemens'
documentation is explicit that PLC-driven changes are never logged. Auditing
them would bury the operator actions in noise.

## 2. How it is built

Three pieces, all generated from source so they survive a rebuild:

- `HmiTag.GmpRelevant = true` on the 624 command tags. This is the whole
  mechanism — flag the tag and WinCC records operator changes itself. No
  scripting. `SetGmpTags.exe` sets it on an existing project; the builder sets
  it on newly created tags.
- `GMPEnabled = true` on the HMI device, set by the builder.
- `StartAuditLog()` on `Screen_Home`'s Loaded event, generated by the builder.

That last one matters more than it looks. `Screen_Home` is built with
`RecreateScreen`, which deletes the screen and its event handlers. Wiring
`StartAuditLog()` by hand meant any Home rebuild silently disarmed the audit
trail — no error anywhere, the log simply stopped. It is generated now.

`InsertElectronicRecord` is **not** used. It returns `0x80000000` on every
call regardless of arguments, calling convention, or whether invoked from
Openness or hand-edited in TIA. It was the wrong mechanism.

## 3. Viewing the records

`AUDIT LOG` in the nav bar (last button, where LOGIN used to be) opens
Siemens' own **Audit Viewer** — a custom web control shipped with TIA V20,
placed with `ContainedType = "Siemens.AuditViewer"`.

Press the **refresh** button (leftmost in its toolbar) to populate the table;
it does not auto-refresh. It offers filtering, column selection, and CSV
export that is integrity-checked for tampering — that export is what a
surveyor or auditor should be given.

A dedicated login screen was removed as redundant: WinCC Unified raises its
own login dialog when an `Authorization`-protected control is touched. The
**LOGOUT** button was kept on the audit screen on purpose. Audit attribution
depends on it — a user left logged in across a watch change means the next
person's valve commands are recorded against the previous operator's name.

## 4. Retention

| Setting | Value |
|---|---|
| Total retention | 365 days |
| Segment | 30 days |
| Total size | ~10 GB (`LogMaxSize` 10000, shown in MB; the database stores KB) |
| Backup | **off** |

Size will never be the limit — 90 records took three days against a 10 GB
ceiling. **Time is what removes records.** After 365 days the oldest segment
is purged, and with backup off there is no copy. Nothing has been purged yet;
the oldest record is 2026-08-21, so the first would go around August 2027.

If the client needs longer than a year, enable backup so closed segments are
archived before purge. Raising the 365 days only moves the cliff.

## 5. Before delivery — do these on the real panel

### 5.1 Storage is on the SD card

Everything below is a **delivery-time** setting. None of it is applied during
development, and section 5.1a explains why in detail: with backup on, neither
log records anything in simulation.

One run of `SetAuditStorage.exe` with TIA open on the project sets all of it:

| | Audit trail | Alarm log |
|---|---|---|
| `StorageDevice` | `SDX51` | `SDX51` |
| `StorageFolder` | `/auditLogLive` | `/alarmLogLive` |
| `BackupMode` | `PrimaryPath` | `PrimaryPath` |
| `PrimaryPath` | `/media/simatic/X51/auditLogBackup` | `/media/simatic/X51/alarmLogBackup` |
| Retention | 365 days | 7 days |

Which lays the card out like this:

```
SD card (X51)
|-- auditLogLive/       audit trail, rolling 365 days
|-- auditLogBackup/     each audit segment archived as it closes
|-- alarmLogLive/       alarm history, rolling 7 days
`-- alarmLogBackup/     each alarm segment archived as it closes
```

Note the two notations. The live log takes a *device* plus a folder relative
to it, so `/auditLogLive` means the card's own root. The backup takes a *full
filesystem path*, so the same place is written `/media/simatic/X51/...`. They
are siblings on one card, not two different media.

**An SD card must be fitted in the X51 slot.** No card means no logs at all,
and nothing warns you except an alarm on the Alarms screen.

#### The alarm log needs one setting changed in the TIA UI first

`StorageDevice = SDX51` on the alarm log is refused by Openness on its own:

```
Database of the log must be on the same medium as the main
database for alarm logging.
```

That main-database medium is a real setting, it is simply not exposed to
Openness. It lives in the TIA UI at:

```
HMI_1 > Runtime settings > Storage system
      > Main database location for alarm logging > Storage medium
```

Set that to **SD-X51** and the Openness write is accepted. Verified
2026-08-24. An earlier version of this document said the alarm log could not
leave USB at all - that was wrong. It could not leave USB *from Openness*,
which is not the same claim.

The constraint is symmetric, so once the main database is on the card the
alarm log cannot be pulled back to USB either. To return to the development
configuration, change that dropdown back to USB-X61 *first*, then run
`SetAuditStorage.exe --revert`. Run in the other order, `--revert` reports
that it could not move the device and leaves it on the card.

#### Folder names need a leading forward slash

`StorageFolder` is writable, but the format is strict and the error message
does not say so:

```
alarmLogLive        refused - "Unable to set PropertyValue"
/alarmLogLive       accepted
backslash form      refused - invalid storage folder
```

An earlier version of this document recorded the property as unsettable. It
is settable; only the format was wrong.

### 5.1a An unreachable backup path stops both logs recording

**Do not turn backup on during development without also changing its path.**
Established by two tests on 2026-08-24.

The first test changed only `BackupMode`, leaving the path at
`/media/simatic/X51/auditLogBackup` and the audit trail on `USBX61` where it
had been recording normally (`SetAuditStorage.exe --backup-only`). The
runtime raised, within one second of starting:

```
RemovableStorage   Storage medium not available. Tag: SD-X51
RemovableStorage   Storage medium not available. Tag: USB-X61
StorageSystem      Host1: AuditTrail: Backup of a segment ... failed
StorageSystem      Host1: AlarmLogging: Backup of a segment ... failed
ServiceManager     Manager (AlarmLoggingManager) is not connected
SystemService      Service (AlarmLogging) is not being executed
SystemService      Service (AuditTrail) is not being executed
```

Both logging services stopped. The audit trail wrote one sign-out row as the
runtime came up and nothing after it; a valve was then operated a full minute
later and no row appeared. Alarm history recorded nothing.

The mechanism appears to be that without backup, WinCC tolerates the missing
removable media and falls back to a local path - on this PC it chose
`C:\UnifiedArchive\AUTDB\HMI_RT_1-SIM_AUT3838\` by itself. With backup on it
has to resolve the physical medium, cannot, and takes the whole logging
service down rather than degrading.

The second test kept backup on but pointed it somewhere that exists -
`C:\UnifiedArchive\TestBackup` (`SetAuditStorage.exe --backup-local`). Both
logs recorded normally throughout: 122 new audit rows and 12 new alarm rows
over four minutes, with backup enabled the whole time, and a `.bak` file
written.

So the cause is the **unreachable path**, not backup. `/media/simatic/X51/`
is a path on the panel's Linux filesystem and cannot resolve on a Windows
simulation. `PrimaryPath` is free text and is not validated against the
target filesystem, so nothing refuses it at engineering time - it fails at
runtime, by taking the logging services down.

This matters for the panel, not just for development. If the mount point is
wrong there, the symptom will be identical: no logging, everything else
apparently normal.

Two further notes from that test:

**Backup fires when a segment closes, not when a row is written.** Shipped
segment periods are 30 days for the trail and 1 day for alarms, so a short
test shows nothing at all. `--backup-local` shortens the period to a minute
and `--revert` restores it.

**Archiving is not immediate on segment close.** Over four minutes, 9 audit
and 5 alarm segments closed and none were archived. The single `.bak` that
appeared was written at startup, for a segment closed before the test began -
a catch-up sweep. Whether archiving runs on a timer or waits until a segment
is no longer the most recent closed one was not established. An empty backup
folder shortly after commissioning is therefore not proof of failure; the
alarm on the ALARMS screen is the reliable signal.

An earlier conclusion is also revised here. `StorageDevice = SDX51` was
recorded as the thing that stopped the trail in simulation, but the two had
only ever been switched on together. Neither is now the culprit - the path
is.

Alarm *annunciation* is unaffected: CM79's direction fault appeared on the
Alarms screen and acknowledged normally throughout. Only logging died.

**Changing `StorageDevice` discards the existing log.** 142 records were lost
this way on 2026-08-23 when the device was switched. Never change it on a
panel carrying history that matters - export first.

#### Checking whether the logs are alive

`check_logs.py` counts rows on disk before and after a runtime session:

```
python check_logs.py --save     take a baseline
python check_logs.py            compare against it
```

It reads a copy of each database *with its WAL*. The runtime holds the live
files open and recent writes sit in the `-wal` until it checkpoints, so
copying the `.db3` alone under-reports and can make a working log look dead.

### 5.2 Verify the backup path

`/media/simatic/X51/auditLogBackup` is **inferred, not verified**. Siemens
documents the panel format as `/media/simatic/<device>/<subfolder>`, and X51
is reported to mount at `/media/simatic/X51/`, but this has not been seen on
a panel. After the panel has run a while, confirm files actually appear
there. A wrong path fails silently.

### 5.3 Check the runtime licence

The engineering PC runs unlicensed, in demo mode. The Audit Viewer does
render in demo mode, so nothing is known to be missing — but a licensed
runtime is required on the delivered panel and licences cannot be inspected
through Openness.

## 6. Known gap — CM numbers

The audit trail records the HMI tag name, `V021`, not the client's `CM79`.
The CM number is project data, not part of the tag name, so the viewer has no
way to know it.

`AUDIT_TAG_MAP.csv` holds the full 89-valve mapping — tag prefix, CM number,
valve tag, location and function — for translating an exported audit trail
or as a reference sheet alongside the panel.

The mapping is **not computable**: no valve's CM number matches its slot
index (slot 1 is CM25, slot 28 is CM01). A lookup table is the only option
short of renaming every tag across every screen and script.

## 7. Still open

- `AlarmLog_Main` is `USBX61`, `NoBackup`, **7-day** retention. Not part of
  the audit work, but it has the same silent USB dependency, and 7 days is
  short for the fault investigations the audit trail is meant to support.
- The Bilge / Fwd / Aft screens still contain dead `InsertElectronicRecord`
  calls in their button scripts. Harmless — those screens are audited
  correctly through the tag mechanism — but they should go on the next full
  rebuild of those screens.
- The Audit Viewer reports "Audit queries cannot be saved. Configure query
  folder in Global Settings / Configuration". This only affects saving named
  queries for reuse; viewing and export are unaffected.
