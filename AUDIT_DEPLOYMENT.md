# Audit Trail — how it works, and what to do before delivery

Operator actions on the HMI are recorded permanently: who did it, what changed,
and when. This note covers what is already configured, what must be changed at
delivery, and what can only be checked on the real panel.

Verified 2026-08-23 by reading the audit database directly, not by assumption.

---

## 1. What is recorded

Every operator command on all 89 valves:

| Action | Tag written |
|---|---|
| OPEN | `V###_OpenCmd` |
| CLOSE | `V###_CloseCmd` |
| ENABLE / DISABLE | `V###_Configured` |
| FAULT RESET | `_TimeoutOpenAlarm`, `_TimeoutCloseAlarm`, `_UnexpMove`, `_DirFault` |

Each record carries the user name, the operator station, the old and new value
and a timestamp. Example, straight out of the database:

```
14:47:44  V021_Configured  User  FALSE -> TRUE   Scripting
14:47:53  V021_OpenCmd     User  FALSE -> TRUE   Scripting
14:48:04  V021_CloseCmd    User  FALSE -> TRUE   Scripting
14:48:15  V021_Configured  User  TRUE  -> FALSE  Scripting
```

Two rows appear per action. `Scripting` with the operator's name is the
intent; `Event Manager` with user `System` is the system's reaction. That
pairing is Siemens' design, not duplication — filter on `Scripting` to see
operator actions alone.

Valve feedback signals (`OpenFB`, `ClosedFB`, `Healthy`, `LocalMode`, `State`)
are deliberately **not** audited. They are driven by the PLC, and Siemens'
documentation is explicit that PLC-driven changes are never logged. Auditing
them would bury the operator actions in noise.

## 2. How it is built

Three pieces, all generated from source so they survive a rebuild:

- `HmiTag.GmpRelevant = true` on the 624 command tags. This is the whole
  mechanism — flag the tag and WinCC records operator changes itself. No
  scripting. `SetGmpTags.exe` sets it on an existing project; the builder sets
  it on newly created tags.
- `GMPEnabled = true` on the HMI device, set by the builder.
- `StartAuditLog()` on `Screen_Home`'s Loaded event, generated by the builder.

That last one matters more than it looks. `Screen_Home` is built with
`RecreateScreen`, which deletes the screen and its event handlers. Wiring
`StartAuditLog()` by hand meant any Home rebuild silently disarmed the audit
trail — no error anywhere, the log simply stopped. It is generated now.

`InsertElectronicRecord` is **not** used. It returns `0x80000000` on every
call regardless of arguments, calling convention, or whether invoked from
Openness or hand-edited in TIA. It was the wrong mechanism.

## 3. Viewing the records

`AUDIT LOG` in the nav bar (last button, where LOGIN used to be) opens
Siemens' own **Audit Viewer** — a custom web control shipped with TIA V20,
placed with `ContainedType = "Siemens.AuditViewer"`.

Press the **refresh** button (leftmost in its toolbar) to populate the table;
it does not auto-refresh. It offers filtering, column selection, and CSV
export that is integrity-checked for tampering — that export is what a
surveyor or auditor should be given.

A dedicated login screen was removed as redundant: WinCC Unified raises its
own login dialog when an `Authorization`-protected control is touched. The
**LOGOUT** button was kept on the audit screen on purpose. Audit attribution
depends on it — a user left logged in across a watch change means the next
person's valve commands are recorded against the previous operator's name.

## 4. Retention

| Setting | Value |
|---|---|
| Total retention | 365 days |
| Segment | 30 days |
| Total size | ~10 GB (`LogMaxSize` 10000, shown in MB; the database stores KB) |
| Backup | **off** |

Size will never be the limit — 90 records took three days against a 10 GB
ceiling. **Time is what removes records.** After 365 days the oldest segment
is purged, and with backup off there is no copy. Nothing has been purged yet;
the oldest record is 2026-08-21, so the first would go around August 2027.

If the client needs longer than a year, enable backup so closed segments are
archived before purge. Raising the 365 days only moves the cliff.

## 5. Before delivery — do these on the real panel

### 5.1 Storage is on the SD card

**Applied 2026-08-23.** `StorageDevice = SDX51`, `BackupMode = PrimaryPath`,
`PrimaryPath = /media/simatic/X51/AuditBackup`.

An SD card must be fitted in the X51 slot. No card means no audit log, and
nothing warns you.

This does **not** work in simulation - a PC has no X51 slot, so the log cannot
open its storage and records nothing. That is expected, not a fault. To test
in simulation, run `SetAuditStorage.exe --revert` (back to USBX61), and run
`SetAuditStorage.exe` again before downloading to the panel.

**Changing StorageDevice discards the existing log.** 142 records were lost
this way on 2026-08-23 when the device was switched. Never change it on a
panel carrying history that matters - export first.

### 5.1b Previous note (kept for context)

Storage was previously `USBX61`. **This is deliberate and must not be changed
during development.** Setting `SDX51` stopped the audit trail recording
completely in simulation — the simulator has no X51 slot, so the log could
not open its storage and never started. No error, no rows, not even a login
entry, while alarm logging on USB kept working normally.

Apply it as a delivery step, with TIA open on the project:

```
SetAuditStorage.exe            # StorageDevice -> SDX51, backup -> /media/simatic/X51/AuditBackup
SetAuditStorage.exe --report   # confirm
SetAuditStorage.exe --revert   # undo, back to USBX61 + NoBackup
```

Then compile and download to the panel.

**An SD card must be fitted in the X51 slot.** No card means no audit log,
and nothing warns you.

### 5.2 Verify the backup path

`/media/simatic/X51/AuditBackup` is **inferred, not verified**. Siemens
documents the panel format as `/media/simatic/<device>/<subfolder>`, and X51
is reported to mount at `/media/simatic/X51/`, but this has not been seen on
a panel. After the panel has run a while, confirm files actually appear
there. A wrong path fails silently.

### 5.3 Check the runtime licence

The engineering PC runs unlicensed, in demo mode. The Audit Viewer does
render in demo mode, so nothing is known to be missing — but a licensed
runtime is required on the delivered panel and licences cannot be inspected
through Openness.

## 6. Known gap — CM numbers

The audit trail records the HMI tag name, `V021`, not the client's `CM79`.
The CM number is project data, not part of the tag name, so the viewer has no
way to know it.

`AUDIT_TAG_MAP.csv` holds the full 89-valve mapping — tag prefix, CM number,
valve tag, location and function — for translating an exported audit trail
or as a reference sheet alongside the panel.

The mapping is **not computable**: no valve's CM number matches its slot
index (slot 1 is CM25, slot 28 is CM01). A lookup table is the only option
short of renaming every tag across every screen and script.

## 7. Still open

- `AlarmLog_Main` is `USBX61`, `NoBackup`, **7-day** retention. Not part of
  the audit work, but it has the same silent USB dependency, and 7 days is
  short for the fault investigations the audit trail is meant to support.
- The Bilge / Fwd / Aft screens still contain dead `InsertElectronicRecord`
  calls in their button scripts. Harmless — those screens are audited
  correctly through the tag mechanism — but they should go on the next full
  rebuild of those screens.
- The Audit Viewer reports "Audit queries cannot be saved. Configure query
  folder in Global Settings / Configuration". This only affects saving named
  queries for reuse; viewing and export are unaffected.
